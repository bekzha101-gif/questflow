# 0001. Единое хранилище в Supabase: построчные таблицы, локальный кеш, очередь и Realtime

## Контекст
Бот должен видеть те же данные, что сайт. Живые данные лежали только в localStorage одного браузера. Старый синк по факту не работал: id задач текстовые, а в схеме `UUID`; в запросе не было `on_conflict`; один общий debounce на четыре отправки терял часть данных; `pullAll` на старте читал при `userId === null`.

## Решение
Все данные живут в Supabase в новой миграции `002_questflow2.sql`: отдельная таблица на каждую сущность, текстовые id, `user_id` и RLS с `WITH CHECK`. Сайт ходит в облако только через модуль `src/store`: локальный кеш в localStorage, очередь отправки и Realtime-подписка. Компоненты не трогают localStorage и сетевые запросы к Supabase напрямую. Старые таблицы 001 не удаляются.

## Почему
- Один JSON-документ на пользователя отвергнут: сайт и бот пишут одновременно, и последняя запись затёрла бы чужую правку целиком. Построчные таблицы не затирают друг друга.
- Починка старого синка отвергнута: сломана сама схема (UUID против текстовых id), строки таблиц 001 пришлось бы переделывать всё равно. Новая схема чище, чем латать старую.
- Облако без локального кеша отвергнуто: сайт перестаёт работать без сети, а офлайн-режим уже был свойством приложения.
- Опрос облака вместо Realtime отвергнут: бот должен видеть свежие данные, а сайт — ответы бота без перезагрузки.

## Последствия
- Весь слой данных сайта переписан; любой новый экран обязан идти через `useCollection` / `useRecord`.
- Миграция 002 необратима для боевой базы; применять её можно только с разрешения пользователя.
- В каждой таблице есть `extra jsonb` для полей без колонки: такие поля не видны как колонки и не индексируются.
- Старые таблицы 001 остаются в базе мёртвым грузом.
