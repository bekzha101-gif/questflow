# 0003. Перенос старых данных из браузера: бэкап, идемпотентность и маркер в облаке

## Контекст
Живые данные лежат в `questflow_*` в localStorage браузера Mac. Пользователь прислать файл отказался («мне всё равно на бэкап»), но требование «не терять» осталось. Сайт может быть открыт на нескольких устройствах.

## Решение
Перенос выполняет сам сайт при входе: сначала скачивает JSON-бэкап, затем записывает строки в новые таблицы. Перенос идемпотентен и без прочитанного облака отклоняется. После успеха в облаке ставится маркер (kv `legacy_imported`). Если маркер уже есть, бэкап всё равно скачивается, а строки не пишутся. Старые ключи копируются в kv как `legacy:<ключ>`; ключи с токенами не переносятся. Перенесённые строки получают `updated_at` 2000-01-01.

## Почему
- Перенос скриптом на сервере отвергнут: данные есть только в браузере Mac, у сервера к ним доступа нет.
- Ждать JSON от пользователя отвергнуто: он прямо отказался его присылать.
- Флаг только в localStorage оказался недостаточным: второй браузер или чистый профиль запустил бы перенос повторно и мог затереть уже живые данные. Поэтому маркер в облаке.
- Дата 2000 для перенесённых строк выбрана затем, чтобы любая настоящая правка выигрывала у переноса (см. 0002).

## Последствия
- Бэкап ложится файлом в загрузки браузера и защищает, только если его сохранят.
- Данные переносятся с того устройства, где они лежат; на другом перенос только скачает бэкап.
- Старые `questflow_*` ключи остаются в браузере; автоматически их удалять нельзя, пока перенос не подтверждён.
- Токены из старых ключей теряются намеренно: их нужно вводить заново.
